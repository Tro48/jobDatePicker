# Будильник

Требование — настоящий будильник, который звонит в точное время, а не
уведомление, которое Android может задержать. Значит, нативный модуль на
`AlarmManager`, dev build и никакого Expo Go.

По функциям это обычный будильник: список произвольной длины, каждую запись
можно править, удалять, ставить на паузу и запускать; своя мелодия, вибрация и
отсрочка. От системного его отличает один режим повтора — **по графику**: такой
будильник звонит в рабочие дни, а не по дням недели, и знает, что перед ночной
сменой вставать надо в другое время, чем перед дневной.

Модуль написан и лежит в `modules/shift-alarm`. Пока не собран APK с ним,
приложение работает как раньше: список сохраняется, расписание считается, но
звонить некому — экран будильника говорит это прямым текстом.

## Почему не уведомления

`expo-notifications` в Doze откладывает срабатывание — система группирует
отложенные задачи в окна пробуждения, и опоздание на 15–20 минут считается
нормой. Режим «Не беспокоить» такое уведомление глушит. Для будильника на смену
это негодно.

## Как это работает

`AlarmManager.setAlarmClock()`, а не `setExactAndAllowWhileIdle()`. Разница
существенная: `setAlarmClock` — единственный API, который система трактует как
настоящий будильник. Он игнорирует Doze и режим экономии, показывает иконку
будильника в статус-баре и переживает «Не беспокоить».

Цепочка срабатывания:

```
AlarmManager.setAlarmClock(время, PendingIntent)
        ↓ срабатывает
BroadcastReceiver
        ↓ немедленно поднимает
Foreground Service (тип mediaPlayback)
        ↓ звук + вибрация + wake lock
Full-screen intent → Activity поверх экрана блокировки
        ↓
кнопки «Отключить» и «Отложить»
```

Foreground service нужен потому, что с Android 8 обычный сервис из бродкаста не
запустить, а звонок должен продолжаться, пока пользователь не встал. Full-screen
intent даёт экран будильника поверх заблокированного телефона, а не шторку.
Кнопки «Отключить» и «Отложить» есть и на этом экране, и в самом уведомлении —
на случай, если полноэкранный intent запрещён.

## Модель будильника

Живёт в `src/domain/alarm.ts`, целиком на JS, без единого импорта React Native.

```ts
interface Alarm {
  id: string;
  label: string;
  /** «ЧЧ:ММ». Одно на будильник во всех режимах повтора. */
  time: string;
  enabled: boolean;
  repeat: AlarmRepeat;
  /** URI системной мелодии. null — сигнал будильника по умолчанию. */
  soundUri: string | null;
  vibrate: boolean;
  snoozeMinutes: number;
}

type AlarmRepeat =
  | { kind: 'once'; date: IsoDate }
  | { kind: 'weekly'; days: Weekday[] }
  | { kind: 'schedule'; times: Record<string, string> };
```

Решения, которые стоит помнить:

- **«Каждый день» — не отдельный режим**, а те же дни недели, только все семь.
  Иначе один и тот же смысл пришлось бы поддерживать в двух ветках планирования.
- **У разового будильника дата хранится явно.** Без неё нельзя отличить «ещё не
  звонил» от «уже отзвонил», а отзвонивший обязан погаснуть сам.
- **Режим «по графику» не спрашивает смены.** Будильник звонит в каждый рабочий
  день выбранного графика; какие это смены, приложение и так знает. `times` —
  время подъёма для конкретного типа смены, оно заполняется, когда в графике
  чередуются дневные и ночные. Пусто — звонит общее время будильника.
- **Время абсолютное, а не «за N минут до смены».** Так его видно сразу и не
  надо считать в уме; расплата — будильник нельзя поставить на вечер
  предыдущего дня. Если заданное время позже начала выбранной смены, экран
  правки говорит об этом прямо.

## Интерфейс модуля

```ts
// modules/shift-alarm/index.ts
export interface NativeAlarm {
  id: string;
  /** Момент срабатывания в миллисекундах эпохи. */
  triggerAtMillis: number;
  title: string;
  /** Подпись на экране будильника: «Дневная смена, начало в 08:00». */
  subtitle: string;
  snoozeMinutes: number;
  soundUri: string | null;
  vibrate: boolean;
}

export const isAlarmModuleAvailable: boolean;
export function getPermissions(): AlarmPermissions;
export function openExactAlarmSettings(): void;
export function openFullScreenIntentSettings(): void;
export function openNotificationSettings(): void;
export function scheduleAlarms(alarms: NativeAlarm[]): Promise<number>;
export function cancelAllAlarms(): Promise<void>;
export function listRingtones(): Promise<Ringtone[]>;
export function previewRingtone(uri: string | null): Promise<void>;
export function stopRingtonePreview(): Promise<void>;
```

Подключение через `requireOptionalNativeModule`, а не `requireNativeModule`:
в сборке без нативной части приложение обязано работать и честно сказать, что
будильника нет, а не падать на старте.

Если система не даёт ставить точные будильники, `scheduleAlarms` бросает
`ERR_EXACT_ALARM_PERMISSION`. Это единственная ошибка, которую JS ловит и
превращает в плашку с кнопкой; остальное — настоящая поломка, глушить её нельзя.

Мелодии отдаются списком, а не системным диалогом
`RingtoneManager.ACTION_RINGTONE_PICKER`: свой экран подчиняется теме
приложения и размеру шрифта и читается скринридером так же, как остальные
списки.

## Разрешения в манифесте

Объявлены в манифесте самого модуля (`modules/shift-alarm/android/src/main/AndroidManifest.xml`)
и подмешиваются в приложение при сборке. Config-плагин не понадобился:
манифест библиотеки сливается с манифестом приложения штатно. Имена классов в
нём записаны полностью — короткая запись в манифесте библиотеки
разворачивается по пакету приложения, а не модуля, и ресиверы бы не нашлись.

| Разрешение | Зачем |
| --- | --- |
| `SCHEDULE_EXACT_ALARM` | точные будильники, Android 12–13 |
| `USE_EXACT_ALARM` | то же для Android 14+, для приложений-будильников выдаётся без запроса у пользователя |
| `USE_FULL_SCREEN_INTENT` | экран будильника поверх блокировки |
| `POST_NOTIFICATIONS` | уведомление foreground-сервиса, Android 13+ |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK` | сервис проигрывания сигнала |
| `WAKE_LOCK` | не дать телефону уснуть во время звонка |
| `VIBRATE` | вибрация |
| `RECEIVE_BOOT_COMPLETED` | перепланировать будильники после перезагрузки |

На Android 12 и 13 `SCHEDULE_EXACT_ALARM` пользователь может отозвать в
настройках. Приложение проверяет `canScheduleExactAlarms()` при каждом
планировании и, если разрешения нет, показывает плашку с кнопкой, ведущей в
`ACTION_REQUEST_SCHEDULE_EXACT_ALARM`. Молча деградировать до неточного
будильника нельзя — проспать смену хуже, чем увидеть предупреждение.

## Из чего собран модуль

| Файл | Ответственность |
| --- | --- |
| `ShiftAlarmModule.kt` | граница с JS: разрешения, постановка набора, мелодии |
| `AlarmScheduler.kt` | `setAlarmClock`, отмена, перепланирование, «отложить» |
| `AlarmStore.kt` | список поставленных будильников в SharedPreferences |
| `AlarmReceiver.kt` | срабатывание: поднимает сервис и больше ничего |
| `AlarmService.kt` | foreground-сервис: звук, вибрация, wake lock, уведомление |
| `AlarmActivity.kt` | экран поверх блокировки, кнопки «Отключить» и «Отложить» |
| `BootReceiver.kt` | перезагрузка, перевод часов, смена пояса, обновление |
| `RingtoneCatalog.kt` | список системных мелодий и их прослушивание |

Экран будильника свёрстан кодом, а не разметкой: четыре элемента, зато у модуля
нет собственных ресурсов и темы, которые пришлось бы сливать с приложением.
Цвета — те же, что в тёмной теме: белый на `#0F1115` даёт 17:1, чёрный на
янтарном — 10.9:1. Размеры в sp, кнопки от 64 dp: спросонья не промахнёшься.

Выбранная мелодия может исчезнуть вместе с картой памяти или удалённым
приложением — тогда звонит сигнал по умолчанию, а не тишина.

`schedule` принимает весь набор целиком и заменяет предыдущий. Инкрементального
API нет намеренно: расписание — производная от списка будильников и графика, и
пересчитать его полностью дешевле и надёжнее, чем поддерживать в согласованном
состоянии.

## Стратегия планирования

Для каждого включённого будильника вперёд ставится **до семи ближайших
срабатываний**, на все будильники разом — **не больше пятидесяти**.

Семь, а не одно, по важной причине: перепланировать умеет только JS, а он
работает, лишь пока открыто приложение. Пока его не открыли, повторяющийся
будильник живёт на этом запасе — неделя для ежедневного, две недели для
графика 2/2. Это осознанный предел: телефон, пролежавший месяц без запуска
приложения, утром не зазвонит.

Перепланирование запускается:

- при запуске приложения — из корня навигации, а не с экрана будильника:
  вкладки монтируются лениво, и приложение, открытое ради календаря, оставляло
  бы систему со вчерашним набором;
- при возврате в приложение из фона;
- по `BOOT_COMPLETED` — при перезагрузке все будильники теряются;
- при переводе часов и смене часового пояса;
- при любой правке будильников, графика, даты первой смены или дней.

Время считается доменной функцией `planAlarms` (`src/domain/alarm.ts`) и
конструктором `Date` по местному времени, а не сложением миллисекунд: в ночь
перевода часов сутки не равны 24 часам, и арифметика по эпохе увела бы
будильник на час.

Прошедшее время не ставится никогда: `AlarmManager` отработал бы его мгновенно
и разбудил посреди дня.

Разовый будильник, чей момент прошёл, выключается сам при ближайшем пересчёте —
`expiredOnceAlarmIds`. Из списка он при этом не пропадает: кнопка запуска
переносит его на ближайший день с тем же временем (`restartOnce`), поэтому
«разбудить в семь» не приходится заводить заново каждый раз. Нативная часть про это ничего не знает: она не умеет
разбудить JS, а хранить в Kotlin вторую копию правил повтора хуже, чем гасить
запись при следующем открытии.

## Где Android подведёт

Честно перечисляю то, что нативным кодом не лечится:

- **Оболочки Xiaomi, Huawei, Oppo, Vivo, Samsung** агрессивно выгружают фоновые
  приложения. Нужно вручную разрешить автозапуск и снять ограничение батареи в
  настройках телефона. Экран будильника говорит об этом прямым текстом — выдать
  себе такое разрешение приложение не может.
- **Принудительная остановка** приложения из настроек отменяет все его
  будильники до следующего запуска. Это поведение системы.
- **Смена часового пояса или перевод времени** сдвигает уже поставленные
  будильники, потому что они живут в абсолютных миллисекундах. Лечится
  перепланированием по `ACTION_TIMEZONE_CHANGED` и `ACTION_TIME_CHANGED`.
- **Экономия энергии в глубоком сне** на некоторых прошивках задерживает даже
  `setAlarmClock`. Массовой проблемы нет, но гарантии уровня системных «Часов»
  дать нельзя — там свои привилегии.
- **Долгий простой без запуска приложения** исчерпывает запас в семь
  срабатываний, см. выше.

## Что проверяется только на устройстве

Kotlin здесь не компилируется: ни JDK, ни Android SDK локально нет. Значит, до
первой сборки не проверено ничего из нативной части — компиляция, слияние
манифестов, реальное срабатывание, экран поверх блокировки, звук, выбор и
прослушивание мелодии, «Отложить», восстановление после перезагрузки. JS-часть,
планирование и экраны проверены тестами и сборкой бандла.
