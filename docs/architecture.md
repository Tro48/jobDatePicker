# Архитектура

## Стек

| Решение | Почему |
| --- | --- |
| React Native через Expo, SDK 54 | Локально нет JDK и Android SDK. Сборка APK уходит в облако EAS, на телефоне ставится dev build, разработка идёт с горячей перезагрузкой по Wi-Fi. |
| Dev build, не Expo Go | Нужен свой нативный код: будильник на AlarmManager в Expo Go невозможен. |
| TypeScript, strict | Домен целиком типизирован, id смен и графиков проверяются на старте. |
| expo-router | Файловая навигация, табы из коробки, дип-линки для будильника (`jobdatepicker://day/2026-09-14`). |
| Zustand + react-native-mmkv | Данных мало: настройки, справочник смен, правки по дням, выплаты. MMKV синхронный, читается на старте без мигания пустым экраном. |
| Свой компонент календаря | Готовые библиотеки придётся ломать под две темы, буквы-маркеры и озвучку TalkBack. Месячная сетка — 200 строк, дешевле написать, чем перебарывать. |
| Свои утилиты дат вместо date-fns в домене | Домен не тянет зависимостей и запускается в голом Node. Для локализованных названий месяцев на экранах хватит `Intl`. |

## Слои

```
app/            маршруты expo-router, только композиция экранов
src/features/   экраны и их локальные компоненты
src/ui/         переиспользуемые компоненты, хук темы
src/theme/      палитра, типографика, отступы
src/data/       хранилище (MMKV), репозитории, миграции схемы
src/domain/     чистая логика: графики, часы, деньги. Не знает про React
modules/alarm/  нативный модуль будильника (Kotlin, Expo Modules API)
```

Правило одно: `src/domain/` не импортирует ничего из React Native. За счёт
этого вся арифметика графиков и денег покрыта тестами, которые бегут за 100 мс
в обычном Node, без эмулятора и без сборки.

## Хранилище

Один MMKV-инстанс, значения — JSON под стабильными ключами:

| Ключ | Содержимое |
| --- | --- |
| `schema.version` | номер версии, для миграций |
| `settings.schedule` | `ActiveSchedule`: id пресета, паттерн, дата первой смены |
| `settings.shiftTypes` | справочник смен с правками пользователя |
| `settings.payroll` | валюта, правила выплат |
| `settings.alarms` | будильники по типам смен |
| `settings.appearance` | тема: системная / светлая / тёмная |
| `overrides` | правки по дням, объект `{ "2026-09-03": DayOverride }` |
| `payments` | массив `PaymentRecord` |

Паттерн графика хранится копией, а не только по `presetId`. Иначе правка
пресета в будущей версии задним числом перепишет уже прожитые месяцы.

Объём: правок и выплат — десятки в год, всё держится в памяти. SQLite здесь
был бы лишним; репозитории в `src/data/` изолируют хранилище на случай, если
данных станет заметно больше.

## Что считается на лету, а что хранится

Календарь не материализуется. Хранятся только график, дата первой смены и
ручные правки; конкретный день вычисляется функцией `resolveDay`. Поэтому смена
графика или сдвиг даты первой смены мгновенно перерисовывает всю историю и не
требует пересчёта базы.

Обратная сторона: изменив дату первой смены, пользователь меняет и прошлое.
Ручные правки при этом остаются на своих датах — они привязаны к дате, а не к
позиции в цикле.
