# Архитектура

## Стек

| Решение | Почему |
| --- | --- |
| React Native через Expo, SDK 57 | Локально нет JDK и Android SDK. Сборка APK уходит в облако EAS, на телефоне ставится dev build, разработка идёт с горячей перезагрузкой по Wi-Fi. |
| Dev build, не Expo Go | Нужен свой нативный код: будильник на AlarmManager в Expo Go невозможен. |
| TypeScript, strict | Домен целиком типизирован, id смен и графиков проверяются на старте. |
| expo-router | Файловая навигация, табы из коробки, дип-линки для будильника (`jobdatepicker://day/2026-09-14`). |
| Zustand + react-native-mmkv 4 | Данных мало: настройки, справочник смен, правки по дням, выплаты. MMKV синхронный, читается на старте без мигания пустым экраном. Версия 4 работает через Nitro и требует dev build — в Expo Go её нет. |
| Свой компонент календаря | Готовые библиотеки придётся ломать под две темы, буквы-маркеры и озвучку TalkBack. Месячная сетка — 200 строк, дешевле написать, чем перебарывать. |
| Свои утилиты дат вместо date-fns в домене | Домен не тянет зависимостей и запускается в голом Node. Для локализованных названий месяцев на экранах хватит `Intl`. |

## Слои

```
app/            маршруты expo-router, только композиция экранов
src/features/   экраны и их локальные компоненты
src/ui/         переиспользуемые компоненты, хук темы
src/theme/      палитра, типографика, отступы
src/data/       хранилище (MMKV), репозитории, миграции схемы
src/domain/     чистая логика: графики, часы, деньги. Не знает про React
modules/shift-alarm/  нативный модуль будильника (Kotlin, Expo Modules API)
```

Правило одно: `src/domain/` не импортирует ничего из React Native. За счёт
этого вся арифметика графиков и денег покрыта тестами, которые бегут за 100 мс
в обычном Node, без эмулятора и без сборки.

## Навигация

Четыре вкладки, а поверх них — шторки: карточка дня, правка будильника,
настройки, деньги по месяцам. Всё это `presentation: 'transparentModal'` со
слайдом снизу; скругления, просвет сверху и шапку с крестиком рисует общий
компонент `Sheet`, а не навигация, — так они одинаковы на всех экранах и не
зависят от версии Android.

Переходы идут через `useGuardedPush`: двойное нажатие по дате открывало два
экрана подряд, потому что оба нажатия успевают отработать до смены экрана.

## Хранилище

Один MMKV-инстанс, значения — JSON под стабильными ключами:

| Ключ | Содержимое |
| --- | --- |
| `schema.version` | номер версии, для миграций |
| `settings.schedule` | `ActiveSchedule`: id пресета, паттерн, дата первой смены |
| `settings.payroll` | валюта, правила выплат |
| `settings.alarms` | список будильников: время, повтор, мелодия, отсрочка |
| `settings.appearance` | тема: системная / светлая / тёмная |
| `overrides` | правки по дням, объект `{ "2026-09-03": DayOverride }` |
| `payments` | массив `PaymentRecord` |

Паттерн графика хранится копией, а не только по `presetId`. Иначе правка
пресета в будущей версии задним числом перепишет уже прожитые месяцы.

Справочник смен, наоборот, **не хранится**: он задан кодом. Снимок из старой
сборки перекрывал новые поля — так у отпуска пропал признак многодневности, и
карточка дня перестала спрашивать количество дней. Правило простое: в хранилище
уходят данные пользователя, справочники живут в коде. Версия схемы поднята до 2,
миграция подставляет справочник из кода поверх любого старого снимка.

Объём: правок и выплат — десятки в год, всё держится в памяти. SQLite здесь
был бы лишним; репозитории в `src/data/` изолируют хранилище на случай, если
данных станет заметно больше.

## Что считается на лету, а что хранится

Календарь не материализуется. Хранятся только график, дата первой смены и
ручные правки; конкретный день вычисляется функцией `resolveDay`. Поэтому смена
графика или сдвиг даты первой смены мгновенно перерисовывает всю историю и не
требует пересчёта базы.

Обратная сторона: изменив дату первой смены, пользователь меняет и прошлое.
Ручные правки при этом остаются на своих датах — они привязаны к дате, а не к
позиции в цикле.

## Фактические версии

Expo SDK 57.0.18, React Native 0.86.3, React 19.2.3, TypeScript 6.0 в строгом
режиме. Новая архитектура и edge-to-edge в SDK 57 включены всегда и в
`app.json` не настраиваются.

Два места, где пришлось вмешаться в зависимости:

- `react-dom` пинится через `overrides` на 19.2.3. `expo-router` тянет
  `react-dom@19.2.8`, которому нужен `react ^19.2.8`, а Expo пинит React 19.2.3.
  Это веб-ветка роутера, на Android она не исполняется, но без пина дерево
  невалидно и любая следующая установка падает с ERESOLVE.
- `react-native-nitro-modules` записан прямой зависимостью, хотя приходит
  транзитивно из `react-native-mmkv` — чтобы автолинковка не зависела от того,
  как npm разложит дерево в следующий раз.

- `react-native-reanimated` и `react-native-worklets` записаны точными
  версиями 4.5.1 и 0.10.1 — это канон SDK 57 из `bundledNativeModules.json`.
  Без пина npm ставил reanimated 4.6.0, тянувший worklets 0.12.1, и облачная
  сборка падала на компиляции C++:
  `no member named 'executeSync' in 'worklets::WorkletRuntime'`.
  `expo-modules-core@57.0.14` собран под API worklets до 0.10, и более свежего
  патча Expo для SDK 57 не существует.

Отдельный вывод из этой поломки: `expo-doctor` проходил 21 проверку из 21 и до
пина, и после. Рассинхрон нативных версий он не ловит — это выясняется только
компиляцией в облаке. Локальные проверки закрывают JS, но не нативную часть.

## Импорты и алиасы

Внутри `src/` и `app/` используется алиас `@/` на папку `src`. Файлы доменного
слоя импортируют друг друга с расширением `.ts` — этого требует запуск тестов в
голом Node через `--experimental-strip-types`. Чтобы то же самое понимал `tsc`,
в `tsconfig.json` включён `allowImportingTsExtensions`; Metro такие пути
резолвит без дополнительной настройки.

## Сборки и выкатка

Из одного кода собираются два приложения с разными идентификаторами пакета,
поэтому они стоят на телефоне рядом и не затирают данные друг друга.

| | Отладочное | Рабочее |
| --- | --- | --- |
| Пакет | `com.andrey.jobdatepicker.dev` | `com.andrey.jobdatepicker` |
| Название | Смены dev | Смены |
| Схема ссылок | `jobdatepickerdev` | `jobdatepicker` |
| Иконка | янтарная шапка | синяя шапка |
| Профиль EAS | `development` | `production` |
| Что внутри | dev-клиент, JS приезжает с Metro | JS зашит в APK, Mac не нужен |

Вариант выбирает переменная `APP_VARIANT`: её задают профиль `development` в
`eas.json` и npm-скрипты запуска, а `app.config.ts` подменяет пакет, название,
схему и иконку. Значение по умолчанию — рабочее приложение: если переменную
забыли, соберётся то, что можно отдать людям, а не отладочная версия.

Схема ссылок у приложений разная намеренно: с одинаковой Android спрашивал бы
при каждом переходе по ссылке, какое из двух открыть.

### Выкатка

```
ветка dev ──пуш──► проверки (типы, тесты, контраст, expo-doctor, бандл)
    │
    └──мерж в main──► те же проверки ──► eas update --branch production
                                          (JS и ассеты, секунды, без квоты)

нативная часть изменилась ──руками──► те же проверки ──► eas build --profile production
```

`checks.yml` вызывается двумя способами: сам по себе на `dev` и в
пул-реквестах, и через `workflow_call` из `update.yml` и `build.yml`. Шаги
описаны один раз, а не скопированы в три места.

Разделение не про красоту процесса: у бесплатного аккаунта Expo 15 сборок в
месяц на платформу, а правки экранов и расчётов — это девять изменений из
десяти. Они уходят обновлением по воздуху и лимит не трогают.

Сборка нужна, когда изменилась нативная часть: модуль будильника, нативные
зависимости, разрешения, иконка, заставка — всё, что попадает в манифест
Android. Такое по воздуху доставить нельзя в принципе: Android разрешает менять
нативный код только установкой подписанного APK.

`--no-wait` в build.yml: workflow ставит сборку в очередь и завершается, не
дожидаясь APK, — иначе двадцать минут ожидания жгли бы минуты GitHub Actions.

Для работы нужен секрет `EXPO_TOKEN` в настройках репозитория — токен доступа
из expo.dev. Без него и сборка, и обновление упадут на шаге авторизации.

### Обновления по воздуху

`runtimeVersion` считается по политике `fingerprint`: EAS берёт отпечаток
нативной части проекта и отдаёт обновление только тем сборкам, у которых он
совпал. С политикой `appVersion` обновление прилетело бы в APK с другой
нативной частью и уронило бы его на старте.

Сборка получает обновления канала, указанного в её профиле `eas.json`:
`production` и `development`. Канал связан с веткой обновлений того же имени.

У этого механизма есть тихий побочный эффект: как только нативная часть
изменилась, старый APK перестаёт получать обновления — молча. Поэтому в
настройках приложения есть карточка «Обновления»: она показывает канал,
отпечаток нативной части, дату текущего выпуска и умеет проверить обновление
руками.

Отдельная карточка «Вышла новая сборка» появляется, когда отпечаток нативной
части в списке выпусков не совпал с установленным. Список выпусков — маленький
JSON, который `build.yml` кладёт в релиз репозитория вместе с самим APK:

```json
{ "runtimeVersion": "…", "url": "https://…/smeny-0.1.0.apk", "version": "0.1.0", "builtAt": "…" }
```

Адрес лежит в `extra.releaseManifestUrl` и указывает на
`releases/latest/download/android.json` — эта ссылка всегда ведёт на последний
релиз, поэтому в приложении её менять не нужно.

APK кладётся в релиз, а не оставляется на EAS, по двум причинам: артефакты EAS
на бесплатном аккаунте живут 30 дней, а ссылка релиза постоянная. Ради этого
репозиторий сделан публичным — иначе приложение не смогло бы прочитать список
выпусков без токена, а токен в клиенте это не секрет, а строчка в бандле.

Файлы называются по приложению и версии: `smeny-0.1.4.apk` и
`smeny-dev-0.1.4.apk`. Отладочные выпуски помечены предварительными — иначе
ссылка `releases/latest` увела бы приложение на отладочный APK вместо рабочего.

### Версия

Патч-версия поднимается автоматически на каждом попадании изменений в `main`:
по ней видно, что именно приехало на телефон, и по ней же называются APK.
Живёт версия только на `main`, на `dev` её никто не трогает — поэтому мержи не
конфликтуют на этой строке. Коммит с новой версией помечен `[skip ci]`, иначе
он запускал бы выкатку заново по кругу.

## Иконка

Рисуется кодом — `scripts/make-icons.ts`, запуск `npm run icons`. Внешних
зависимостей нет: PNG собирается вручную поверх `zlib` из стандартной
библиотеки, фигуры считаются знаковым расстоянием, из него же берётся
сглаживание краёв.

Так сделано не из любви к велосипедам: иконку можно поправить в цвете и
пропорциях одной строкой и увидеть, из чего она собрана, а не хранить бинарник
неизвестного происхождения, который нечем перерисовать.

Рисунок — календарный лист с шапкой и сеткой клеток. Клетки раскрашены не
случайно: это график 2/2 день-ночь — две дневные, два выходных, две ночные.
Цвета взяты из палитры приложения, фон совпадает с `background` тёмной темы.

| Файл | Что это |
| --- | --- |
| `icon.png` | обычная иконка, рисунок на тёмном фоне |
| `android-icon-foreground.png` | передний слой адаптивной иконки, рисунок мельче — края съест маска |
| `android-icon-background.png` | задний слой, сплошной `#0F1115` |
| `android-icon-monochrome.png` | тематическая иконка Android 13+: силуэт с вырезанными клетками, цвет система задаёт сама |
| `splash-icon.png` | заставка на светлой теме: лист тёмный, иначе на белом фоне его не видно |
| `splash-icon-dark.png` | заставка на тёмной теме, тот же рисунок, что в иконке |

Адаптивная иконка обрезается маской до круга или скруглённого квадрата,
поэтому рисунок на переднем слое занимает половину стороны: дальние точки
скруглённых углов листа ложатся в 320 пикселей от центра при радиусе маски 341.
Заставка на Android 12+ обрезается так же, поэтому запас по краям у неё тот же.

Заставка настраивается плагином `expo-splash-screen` в `app.json`, с отдельными
картинкой и фоном на светлую и тёмную тему. JS в этом не участвует: заставку
скрывает система, когда приложение отрисовало первый кадр. Прятать её руками
незачем — хранилище на MMKV читается синхронно, пустого состояния не мелькает.
